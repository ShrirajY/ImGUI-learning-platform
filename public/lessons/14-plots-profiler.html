Why every engine has a profiler panel

"It feels slow" doesn't help you fix anything. A number does, and a graph of that number over time helps even more. Dear ImGui has two simple plotting widgets, a progress bar and the window flags you need for a heads-up display, which is enough to build a useful profiler.

The engine's frame-time ring buffer

Every frame, OGL.c writes the frame time in milliseconds into a fixed array and advances a write index:

#define FRAME_HISTORY 120
float gFrameTimes[FRAME_HISTORY];     // milliseconds, ring buffer
int   gFrameTimeOffset = 0;           // next write position

gFrameTimes[gFrameTimeOffset] = gDeltaTime * 1000.0f;
gFrameTimeOffset = (gFrameTimeOffset + 1) % FRAME_HISTORY;

So gFrameTimeOffset always points at the oldest sample. That is exactly what the plot functions want as values_offset.

PlotLines and PlotHistogram

void PlotLines    (const char* label, const float* values, int values_count, int values_offset = 0,
                   const char* overlay_text = NULL, float scale_min = FLT_MAX, float scale_max = FLT_MAX,
                   ImVec2 graph_size = ImVec2(0, 0), int stride = sizeof(float));
void PlotHistogram(/* same parameters */);
ParameterUse it for
values_offsetIndex of the first (oldest) value to draw. It wraps around, so a ring buffer scrolls naturally.
overlay_textText drawn centred on top of the plot, e.g. "avg 16.6 ms"
scale_min / scale_maxFixed vertical range. FLT_MAX auto-fits to the data. A fixed scale keeps spikes in proportion.
graph_sizeImVec2(-FLT_MIN, 90) = full width, 90 px tall
stridePlot one field from an array of structs, e.g. sizeof(MyStats)
char overlay[64];
_snprintf(overlay, sizeof(overlay) - 1, "avg %.2f ms", avgMs);
ImGui::PlotLines("##frametimes", gFrameTimes, FRAME_HISTORY, gFrameTimeOffset,
                 overlay, 0.0f, 33.3f, ImVec2(-FLT_MIN, 90));
Fixed scale or auto scale?

Auto scale turns a steady 16.6 ms with 0.1 ms of jitter into a wildly jumping line. For frame times, fix the range from 0 to roughly two frame budgets (33 ms at 60 FPS). Spikes then look like spikes and noise looks like noise.

Min / avg / max

One loop over the buffer gives the three numbers people actually read. Max matters most for games: an average of 8 ms with one 60 ms hitch every second still feels like stutter.

ProgressBar as a budget meter

float used = avgMs / (1000.0f / targetFps);          // 1.0 = exactly on budget
ImGui::PushStyleColor(ImGuiCol_PlotHistogram, used <= 1.0f ? green : red);  // bar fill colour
ImGui::ProgressBar(used > 1.0f ? 1.0f : used, ImVec2(-FLT_MIN, 0), "12.1 / 16.7 ms");
ImGui::PopStyleColor();

ProgressBar(fraction, size, overlay) takes a fraction from 0 to 1. Pass NULL as the overlay for an automatic percentage, or "" for no text at all. That's useful for the thin per-section bars in the lesson.

A heads-up overlay

A HUD is just a window with the decorations and interactions removed and its position forced every frame:

ImGuiWindowFlags flags = ImGuiWindowFlags_NoDecoration        // no title bar, resize, scrollbars
                       | ImGuiWindowFlags_AlwaysAutoResize    // fit the content
                       | ImGuiWindowFlags_NoSavedSettings     // don't remember it in imgui.ini
                       | ImGuiWindowFlags_NoFocusOnAppearing  // don't steal focus
                       | ImGuiWindowFlags_NoNav               // skip in keyboard navigation
                       | ImGuiWindowFlags_NoMove;

const ImGuiViewport *vp = ImGui::GetMainViewport();
ImVec2 pos(vp->WorkPos.x + vp->WorkSize.x - 10, vp->WorkPos.y + 10);   // top-right corner
ImGui::SetNextWindowPos(pos, ImGuiCond_Always, ImVec2(1.0f, 0.0f));    // pivot = window's top-right
ImGui::SetNextWindowBgAlpha(0.35f);
ImGui::Begin("##PerfHUD", NULL, flags);
  • WorkPos / WorkSize describe the usable screen area. If you add a main menu bar later (lesson 18), they shrink to exclude it and the HUD moves below it automatically.
  • The pivot says which point of the window lands on pos. (0,0) is the window's top-left and (1,1) its bottom-right. With the right pivot you never need to know the window's size.
  • BeginPopupContextWindow() opens a menu when you right-click anywhere in the window. The lesson uses it to pick a corner.

A scope profiler in 30 lines

Frame time tells you that a frame was slow, not why. Wrap sections of code in begin/end markers that read the high-resolution counter (windows.h is already included):

static LONGLONG L14_Now(void) { LARGE_INTEGER t; QueryPerformanceCounter(&t); return t.QuadPart; }

void L14_Begin(const char *name) { L14_Get(name)->start = L14_Now(); }
void L14_End(const char *name)
{
    L14_Section *s = L14_Get(name);
    s->lastMs = (float)((L14_Now() - s->start) * 1000.0 / L14_freq.QuadPart);
    s->history[s->historyOffset] = s->lastMs;                 // its own ring buffer
    s->historyOffset = (s->historyOffset + 1) % FRAME_HISTORY;
}

// C++ RAII version: End() runs automatically when the scope closes
struct L14_Scope { const char *name; L14_Scope(const char *n) : name(n) { L14_Begin(n); } ~L14_Scope() { L14_End(name); } };

Each section keeps its own history, so you can plot it with the same PlotLines call. Call QueryPerformanceFrequency once in Lesson_Init() to convert ticks to milliseconds.

VSync and what you are really measuring

With VSync on (gVSync = true), SwapBuffers waits for the monitor, so the frame time sits at 16.7 ms on a 60 Hz screen no matter how little work you do. Turn it off and the frame time drops to your real CPU+GPU cost. Then move the Fake work slider and watch the "Fake work" section and the frame graph climb together.

Scope timers measure CPU time only

OpenGL calls return before the GPU has finished. A glDrawArrays can "cost" 0.01 ms on the CPU while the GPU spends 5 ms on it. Measuring GPU time takes timer queries (GL_TIME_ELAPSED), which are beyond fixed-function GL.

Game-engine angle

Real engines build exactly this, just bigger. They use named scopes with nesting (a stack), per-thread timelines and a capture button that freezes a few seconds of history to inspect. When you outgrow it, reach for Tracy or Optick, which use the same "macro at the top of a scope" idea. Keep the always-on corner HUD as well: it is the first thing you look at when a level suddenly feels heavy, and it costs almost nothing.

Challenges

  1. Add a "Freeze" checkbox. Each frame, copy gFrameTimes into a private array and plot that array instead. While Freeze is on, stop copying, so the graph holds still and you can inspect a spike.
  2. Count hitches: frames in the buffer slower than 2x the average. Show the count in the HUD in red when it isn't zero.
  3. Add a "Scene" section that times a loop computing the distance from the camera target to every entity, and display the result as a PlotHistogram of distances (one bar per entity).
Show solution 
// 1) freeze
static bool  freeze = false;
static float frozen[FRAME_HISTORY];
static int   frozenOffset = 0;
ImGui::Checkbox("Freeze", &freeze);
if (!freeze) { memcpy(frozen, gFrameTimes, sizeof(frozen)); frozenOffset = gFrameTimeOffset; }
ImGui::PlotLines("##frozen", frozen, FRAME_HISTORY, frozenOffset, NULL, 0.0f, 33.3f, ImVec2(-FLT_MIN, 90));

// 2) hitches (inside the HUD window)
float avg = Engine_AverageFrameTimeMs();
int hitches = 0;
for (int i = 0; i < FRAME_HISTORY; i++) if (gFrameTimes[i] > avg * 2.0f) hitches++;
if (hitches) ImGui::TextColored(ImVec4(1, 0.3f, 0.3f, 1), "%d hitches", hitches);

// 3) distances
static float dist[MAX_ENTITIES];
L14_Begin("Scene");
for (int i = 0; i < gEntityCount; i++)
{
    float dx = gEntities[i].position[0] - gCamera.target[0];
    float dy = gEntities[i].position[1] - gCamera.target[1];
    float dz = gEntities[i].position[2] - gCamera.target[2];
    dist[i] = sqrtf(dx * dx + dy * dy + dz * dz);
}
L14_End("Scene");
ImGui::PlotHistogram("Distances", dist, gEntityCount, 0, NULL, 0.0f, FLT_MAX, ImVec2(-FLT_MIN, 60));
