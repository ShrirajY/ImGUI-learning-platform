Architecture in four ideas

1. One struct for all editor state

Panel visibility, console filter, rename buffer, play-mode snapshot: everything the editor needs, and the game does not, lives in Ed_State:

struct Ed_State
{
    bool showHierarchy, showInspector, showConsole, showRender, showAssets, showStats;
    bool editorVisible;                 // F1
    bool playing;                       // play mode
    Entity snapshot[MAX_ENTITIES];      // scene copy taken when Play is pressed
    ImGuiTextFilter consoleFilter;
    char consoleInput[128];
    ...
};
static Ed_State ed;

This draws a clear line: engine data (gEntities, gCamera, gLight) is what the game runs on, and editor data (ed) is only about how you view and edit it. A shipped game wouldn't contain ed at all.

2. One function per panel

void Lesson_UI(void)
{
    Ed_HandleShortcuts();
    if (ed.editorVisible)
    {
        Ed_MainMenuBar();                       // first: it reserves space at the top
        if (ed.showHierarchy) Ed_PanelHierarchy();
        if (ed.showRender)    Ed_PanelRender();
        if (ed.showInspector) Ed_PanelInspector();
        if (ed.showConsole)   Ed_PanelConsole();
        if (ed.showAssets)    Ed_PanelAssets();
        if (ed.showStats)     Ed_StatsOverlay();
        if (ed.showLabels && !ed.playing) Ed_EntityLabels();
    }
    Ed_FlushCommands();                         // structural changes run last
}

Panels don't call each other. They communicate only through shared state: gSelectedEntity is the "selection bus" that the hierarchy writes, 3D picking writes, and the inspector reads. Adding a new panel means adding one function and one show flag.

Pass &ed.showX to Begin

ImGui::Begin("Inspector", &ed.showInspector) gives the window a close button that writes into the same bool the View menu toggles with MenuItem("Inspector", NULL, &ed.showInspector). One variable, two UIs, always in sync.

3. Deferred commands

Deleting entity #3 while the hierarchy loop is at row #3 shifts every later entity down by one. The rest of the loop then draws wrong names, and IDs jump. Duplicating can grow the array mid-loop. So structural changes are recorded and executed after all panels have run:

enum Ed_CmdType { ED_CMD_CREATE, ED_CMD_DUPLICATE, ED_CMD_DELETE, ED_CMD_FOCUS, ED_CMD_RESET, ED_CMD_CLEAR, ED_CMD_QUIT };
struct Ed_Command { int type; int arg; };

if (ImGui::MenuItem("Delete", "Del")) Ed_Queue(ED_CMD_DELETE, i);   // inside the loop: just record

static void Ed_FlushCommands(void)                                 // end of frame: execute
{
    for (int c = 0; c < Ed_queueCount; c++)
        switch (Ed_queue[c].type) { case ED_CMD_DELETE: Engine_RemoveEntity(Ed_queue[c].arg); break; ... }
    Ed_queueCount = 0;
}

Simple edits like dragging a position or typing a name still write directly. Only operations that change the shape of the data are deferred. The same queue is the natural place to add undo/redo later: each command knows how to do and undo itself.

4. Edit mode vs play mode

Every serious engine separates editing the level from running it. Pressing Play takes a snapshot, and pressing Stop restores it, so whatever the game did while running is thrown away:

static void Ed_Play(void)
{
    memcpy(ed.snapshot, gEntities, sizeof(Entity) * gEntityCount);
    ed.snapshotCount = gEntityCount;
    ed.playing = true;
    gPaused = false;                     // behaviours (spin) only run while playing
}
static void Ed_Stop(void)
{
    memcpy(gEntities, ed.snapshot, sizeof(Entity) * ed.snapshotCount);
    gEntityCount = ed.snapshotCount;
    ed.playing = false;
    gPaused = true;
}

While playing, the menu bar is tinted red (a PushStyleColor(ImGuiCol_MenuBarBg) around BeginMainMenuBar), because "I tweaked everything during play and lost it on Stop" is a classic engine-user mistake. Make the state obvious.

Laying out around the 3D view

There is no docking in this ImGui version, so the editor computes a default layout from the viewport's work area:

static void Ed_NextWindowRect(float x, float y, float w, float h)
{
    ImGuiCond cond = (ed.resetLayout || ed.layoutWarmup > 0) ? ImGuiCond_Always : ImGuiCond_FirstUseEver;
    const ImGuiViewport *vp = ImGui::GetMainViewport();
    ImGui::SetNextWindowPos(ImVec2(vp->WorkPos.x + x, vp->WorkPos.y + y), cond);
    ImGui::SetNextWindowSize(ImVec2(w, h), cond);
}

Ed_NextWindowRect(0, 0, ED_LEFT_W, 420);                                          // hierarchy: left
Ed_NextWindowRect(vp->WorkSize.x - ED_RIGHT_W, 0, ED_RIGHT_W, vp->WorkSize.y);    // inspector: right
Ed_NextWindowRect(ED_LEFT_W, vp->WorkSize.y - ED_BOTTOM_H, midW * 0.6f, ED_BOTTOM_H); // console: bottom
  • BeginMainMenuBar() reserves the top strip, and WorkPos/WorkSize exclude it, so panels start below the menu.
  • ImGuiCond_FirstUseEver means "only if the window has no saved position", so the user can still rearrange everything.
  • View > Reset Layout sets a flag that switches to ImGuiCond_Always for one frame.
The work area updates one frame late

The menu bar's height is subtracted from WorkPos/WorkSize starting on the next frame. On frame 1, FirstUseEver would place the panels under the menu bar and keep them there. The editor forces the layout for its first two frames (ed.layoutWarmup) to get around this.

Shortcuts that respect typing

static void Ed_HandleShortcuts(void)
{
    ImGuiIO &io = ImGui::GetIO();
    if (io.WantTextInput) return;                                   // typing a name: no hotkeys
    if (ImGui::IsKeyPressed(ImGuiKey_F1, false)) ed.editorVisible = !ed.editorVisible;
    if (ImGui::IsKeyChordPressed(ImGuiMod_Ctrl | ImGuiKey_D)) Ed_Queue(ED_CMD_DUPLICATE, gSelectedEntity);
    if (ImGui::IsKeyPressed(ImGuiKey_Delete, false))           Ed_Queue(ED_CMD_DELETE, gSelectedEntity);
}

Why WantTextInput and not WantCaptureKeyboard? With keyboard navigation enabled, any focused panel captures the keyboard, but you still want Del to work right after clicking a row in the hierarchy. You only want it to stop while a text field is being edited.

Game-engine angle: editor layer vs runtime

In a real engine, everything prefixed Ed_ lives in a separate editor module (often a separate DLL or a #if WITH_EDITOR build), and the runtime knows nothing about it. The runtime exposes a scene, systems and an API, the same role as the Engine_* block in OGL.c. The editor is just another client of that API. That's why F1 can hide the whole editor with one bool, and why a shipped build can leave it out entirely. In practice:

  • Play mode serialises the scene (to memory or disk) and restores it on Stop. The snapshot here is the in-memory version.
  • Commands become an undo stack, and later the basis for multi-user editing or scripting. The console's spawn sphere and the menu's Create > Sphere go through the same queue.
  • Selection grows into a set (multi-select) with a "selection changed" event, but a single global index carries you a long way.
  • The 3D view moves into its own ImGui window via a render target. That's lesson 19's "Game View".

{
    for (int i = gEntityCount; i > ed.undoIndex; i--) gEntities[i] = gEntities[i - 1];
    gEntities[ed.undoIndex] = ed.undoEntity;
    gEntityCount++;
    gSelectedEntity = ed.undoIndex;
    ed.canUndo = false;

static void Ed_Toolbar(void)
{
    const ImGuiViewport *vp = ImGui::GetMainViewport();
    ImGui::SetNextWindowPos(ImVec2(vp->WorkPos.x + ED_LEFT_W, vp->WorkPos.y));
    ImGui::SetNextWindowSize(ImVec2(vp->WorkSize.x - ED_LEFT_W - ED_RIGHT_W, 0));
    ImGui::Begin("##toolbar", NULL, ImGuiWindowFlags_NoDecoration | ImGuiWindowFlags_NoMove | ImGuiWindowFlags_NoSavedSettings);
    bool *toggles[2] = { &gShowGrid, &gWireframe };
    const char *names[2] = { "Grid", "Wire" };
    for (int i = 0; i < 2; i++)
    {
        bool on = *toggles[i];
        if (on) ImGui::PushStyleColor(ImGuiCol_Button, ImGui::GetStyleColorVec4(ImGuiCol_HeaderActive));
        if (ImGui::Button(names[i])) *toggles[i] = !*toggles[i];
        if (on) ImGui::PopStyleColor();
        ImGui::SameLine();
    }
    for (int m = 0; m < MESH_COUNT; m++) { ImGui::SameLine(); if (ImGui::Button(gMeshNames[m])) Ed_Queue(ED_CMD_CREATE, m); }
    ImGui::End();
