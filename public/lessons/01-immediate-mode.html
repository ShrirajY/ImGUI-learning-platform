Two ways to build a GUI

Most GUI toolkits you may have used (Win32 controls, MFC, Qt, WinForms, HTML) are retained mode. You create widget objects once, the toolkit keeps them alive, and it calls you back when something happens. Dear ImGui is immediate mode. There are no widget objects. Every frame you call functions that describe the UI, and each call returns what the user just did.

// 1. Create the control ONCE (e.g. in WM_CREATE)
HWND hButton = CreateWindow(TEXT("BUTTON"), TEXT("Spawn cube"),
                            WS_CHILD | WS_VISIBLE, 10, 10, 120, 30,
                            hwnd, (HMENU)ID_SPAWN, hInstance, NULL);

// 2. React to it somewhere else, in a callback
case WM_COMMAND:
    if (LOWORD(wParam) == ID_SPAWN)
        Engine_AddEntity("Cube", MESH_CUBE);
    break;

// 3. Keep it in sync by hand: when gEntityCount changes, update the label...
SetWindowText(hLabel, buffer);
// ...and remember to DestroyWindow() it when you no longer need it.

The UI state is spread over three places: the control object, the callback, and your data. You have to keep them in sync.

// Called EVERY frame, from the render loop
void Lesson_UI(void)
{
    ImGui::Begin("Spawner");
    if (ImGui::Button("Spawn cube"))                 // draws the button AND reports the click
        Engine_AddEntity("Cube", MESH_CUBE);
    ImGui::Text("Entities: %d", gEntityCount);       // always shows the current value
    ImGui::End();
}

Creation, drawing and event handling all happen in one line. To remove the button, stop calling Button(). To show it conditionally, put it inside an if.

"Immediate" is about the API, not the drawing

ImGui doesn't draw each widget the moment you call it. It collects everything into vertex buffers and draws it all at the end of the frame in a few draw calls. "Immediate mode" means that you don't keep widget objects around. This is similar to old glBegin()/glEnd(), where you re-submitted the geometry every frame instead of building a scene graph.

The architecture: core + two backends

Dear ImGui is split into three layers. You compile all of them into your program:

LayerFilesJob
Coreimgui.cpp, imgui_widgets.cpp, imgui_draw.cpp, imgui_tables.cpp, imgui_demo.cppWidgets, layout, IDs, fonts, building vertex buffers. Knows nothing about Windows or OpenGL.
Platform backendimgui_impl_win32.cppFeeds Win32 messages (mouse, keyboard, focus, cursor) and window size + time into ImGui.
Renderer backendimgui_impl_opengl2.cppUploads the font texture and draws ImGui's triangles with fixed-function OpenGL (glVertexPointer, glDrawElements).

Because the core is separate from the backends, the same UI code runs on DirectX, Vulkan, SDL or GLFW. You only swap the two backend files.

ImGuiIO: the bridge

ImGuiIO is one struct, returned by ImGui::GetIO(), that holds the inputs and outputs between your application and ImGui:

FieldDirectionMeaning
io.DisplaySizeinWindow client size in pixels (set by the Win32 backend)
io.DeltaTimeinSeconds since last frame
io.MousePos, io.MouseDown[]inMouse state, from WndProc messages
io.ConfigFlagsinOptions such as ImGuiConfigFlags_NavEnableKeyboard
io.WantCaptureMouseoutTrue when the mouse is over/using ImGui, so the game should ignore it
io.WantCaptureKeyboardoutTrue when ImGui wants the keyboard (e.g. typing in a text field)
io.FramerateoutRolling-average FPS
Game-engine angle

Every engine with ImGui needs this check: "Is this click for the UI or for the game?". The mini engine's camera code does it:

if (!io.WantCaptureMouse)      // mouse is over the 3D view, not over a panel
{
    // orbit / pan / zoom / pick entities
}
if (!io.WantCaptureKeyboard)   // the user is not typing in an InputText
{
    // WASD camera movement
}

Without it, typing "dog" into an entity name field would also move the camera with the D key.

Where does the state live?

A common question is: "If nothing is retained, how does a checkbox remember it's checked?" The answer is that you store it:

ImGui::Checkbox("Wireframe", &gWireframe);   // the bool is YOUR variable

ImGui reads gWireframe to draw the box and writes to it when it's clicked. The engine variable is the UI state. ImGui itself keeps only a small amount of internal state, indexed by ID (lesson 06):

  • window positions, sizes, collapsed state and scroll,
  • which widget is hovered or active right now (e.g. the slider you're dragging),
  • tree node open/closed flags, and the text cursor of an active InputText.
static vs global

For UI-only values (a "show window" flag, a search buffer) a static local inside Lesson_UI() is the simplest choice. It keeps its value between frames just like a global. For real engine data, point widgets directly at the engine's variables.

Performance myths

  • "Rebuilding the UI every frame must be slow." A typical editor UI costs a fraction of a millisecond of CPU time. Widgets that are scrolled out of view or in collapsed windows are skipped almost for free.
  • "It must issue thousands of draw calls." No. Everything is batched into one vertex buffer, and there is roughly one draw call per window (more only when clipping or textures change). Open ShowMetricsWindow() to see the exact numbers.
  • "Immediate mode means no caching." ImGui caches glyphs, text sizes, and window and table state. What it doesn't cache is your data, so it can never be out of date.
  • When it does cost: listing 100,000 items without clipping. ImGuiListClipper, covered with tables and the console later in the course, fixes that by only submitting the visible rows.
