The editor pair

Open any engine editor and you will find the same two panels: a Hierarchy (or Outliner, or Scene Tree) listing every object, and an Inspector (or Details, or Properties) showing the selected object's fields. They are connected by one value: the selection. In our engine that is gSelectedEntity, and the 3D view writes to it too when you click an object.

Editor state vs scene data

Before writing any code, decide where each piece of state lives. This split will save you a lot of trouble later, when you add saving, undo and play mode:

Scene data (engine)Editor state (UI only)
gEntities[]: name, transform, mesh, colour, textureWhich entity is being renamed, and its edit buffer
gEntityCount"Group by mesh" toggle, open/closed tree nodes
gSelectedEntity (shared with picking)Pending delete / duplicate requests
"Scroll to selection" flag

Scene data gets saved to disk and simulated. Editor state never does. In the lesson code, all editor state sits in one struct, L09_EditorState, so it is obvious what belongs to the UI. ImGui widgets edit the scene data directly through pointers, so there is no copy to keep in sync.

TreeNodeEx and its flags

TreeNode("label") is fine for debug trees. For a hierarchy you want control over how nodes look and react, so use TreeNodeEx(id, flags, fmt, ...):

ImGuiTreeNodeFlags_Why a hierarchy wants it
OpenOnArrowA single click selects; only clicking the arrow opens/closes
OpenOnDoubleClickDouble-click on the label also toggles open
SpanAvailWidthHighlight and hit-box extend to the right edge (full-row selection)
LeafNo arrow; the node has no children
NoTreePushOnOpenDon't indent or push an ID, so you don't call TreePop() (handy for leaves)
SelectedDraw the row highlighted. You set this from your own selection
DefaultOpenStart expanded the first time
ImGuiTreeNodeFlags flags = ImGuiTreeNodeFlags_Leaf | ImGuiTreeNodeFlags_NoTreePushOnOpen
                         | ImGuiTreeNodeFlags_SpanAvailWidth;
if (gSelectedEntity == i) flags |= ImGuiTreeNodeFlags_Selected;

ImGui::PushID(i);
ImGui::TreeNodeEx("##node", flags, "%s", e->name);   // ID = "##node" inside PushID(i)
if (ImGui::IsItemClicked() && !ImGui::IsItemToggledOpen())
    gSelectedEntity = i;                              // click selects
if (ImGui::IsItemHovered() && ImGui::IsMouseDoubleClicked(ImGuiMouseButton_Left))
    Engine_FocusEntity(i);                            // double-click focuses the camera
ImGui::PopID();

IsItemClicked() fires on mouse-down over the item. The !IsItemToggledOpen() check stops a click on a node's arrow from also changing the selection. That matters for parent nodes, which have an arrow.

Leaf + NoTreePushOnOpen, or TreePop?

A normal node that returns true must be closed with TreePop(). With NoTreePushOnOpen, nothing was pushed, so you must not call TreePop(). Mixing these up corrupts the ID stack. ImGui asserts at the end of the frame, and the message is not always obvious.

Our scene is flat

The mini engine has no parent/child links, so the code shows a root "Scene" node and, optionally, one folder node per mesh type. In a real engine, each entity stores a parent and a firstChild/nextSibling. You then draw the tree with a recursive function: TreeNodeEx with no Leaf flag if the entity has children, recurse into the children, then TreePop.

Selection that flows both ways

Because the hierarchy reads gSelectedEntity every frame to decide which row gets the Selected flag, clicking a mesh in the 3D view highlights its row on the next frame with no extra code. The one extra touch is scrolling the row into view. To detect a selection change that came from outside, compare against last frame's value:

if (gSelectedEntity != ed.prevSelection) ed.scrollToSelection = true;
// ... while drawing row i:
if (i == gSelectedEntity && ed.scrollToSelection) { ImGui::SetScrollHereY(); ed.scrollToSelection = false; }
// ... end of frame:
ed.prevSelection = gSelectedEntity;

Context menus

There are two kinds of right-click menu:

// 1. On an item: call right after the item (uses the last item's ID)
if (ImGui::BeginPopupContextItem("##rowmenu"))
{
    if (ImGui::MenuItem("Rename", "F2"))  StartRename(i);
    if (ImGui::MenuItem("Duplicate"))     ed.pendingDuplicate = i;
    if (ImGui::MenuItem("Focus"))         Engine_FocusEntity(i);
    if (ImGui::MenuItem("Delete", "Del")) ed.pendingDelete = i;
    ImGui::EndPopup();
}

// 2. On empty space in the window (NoOpenOverItems = don't trigger over rows)
if (ImGui::BeginPopupContextWindow("##create", ImGuiPopupFlags_MouseButtonRight | ImGuiPopupFlags_NoOpenOverItems))
{
    for (int m = 0; m < MESH_COUNT; m++)
        if (ImGui::MenuItem(gMeshNames[m])) CreateEntity(m);
    ImGui::EndPopup();
}
Passing flags to BeginPopupContext*

The default flags value is 1, which is ImGuiPopupFlags_MouseButtonRight. As soon as you pass your own flags you replace that default, so add MouseButtonRight back explicitly, as above.

Deferred deletion: never remove while iterating

This is the classic editor bug. You are inside for (i = 0; i < gEntityCount; i++), the user clicks "Delete" on row 2, and you call Engine_RemoveEntity(2) right there. Everything after index 2 shifts down by one. The loop then skips an entity, draws one row with the wrong ID, and the Inspector, drawn later in the same frame, may read past the end of the array.

The fix is to record the request and apply it after all windows have been drawn:

// inside the loop / inspector:
if (ImGui::MenuItem("Delete")) ed.pendingDelete = i;

// once per frame, after every window:
void ApplyPendingActions(void)
{
    if (ed.pendingDelete >= 0) Engine_RemoveEntity(ed.pendingDelete);
    ed.pendingDelete = -1;
}

The same goes for Duplicate and Create, because adding entities while iterating is just as dangerous with dynamic arrays (a std::vector may reallocate and leave your Entity* pointing at freed memory). Later, this "list of pending commands" is exactly what grows into an undo/redo system.

Inline rename

When renaming, draw an InputText in place of the tree node. Focus it on the first frame, commit on Enter, and cancel when it loses focus:

if (ed.renameIndex == i)
{
    if (ed.renameFocus) { ImGui::SetKeyboardFocusHere(); ed.renameFocus = false; }
    if (ImGui::InputText("##rename", ed.renameBuf, sizeof(ed.renameBuf),
                         ImGuiInputTextFlags_EnterReturnsTrue | ImGuiInputTextFlags_AutoSelectAll))
    { strcpy(e->name, ed.renameBuf); ed.renameIndex = -1; }
    else if (ImGui::IsItemDeactivated())
        ed.renameIndex = -1;          // Escape or clicked elsewhere
}

The Inspector

The Inspector is a property grid (lesson 7) pointed at &gEntities[gSelectedEntity]. Two details matter:

  • Always validate the index (0 <= sel < gEntityCount) at the top. The selection can be -1, or stale after a delete.
  • PushID(selectedIndex) around the whole panel. If you are dragging the Position field and the selection changes under the mouse, ImGui would otherwise treat the "same" widget of the new entity as still active.
Game-engine angle

This pair is the backbone of every editor you will build. Hierarchy = view of the scene graph + selection + structural commands (create, delete, duplicate, reparent). Inspector = view of one object's components, with each CollapsingHeader being a component (Transform, Mesh Renderer, Behaviour). When you add a real component system, the Inspector becomes a loop over the entity's components, each one drawing its own header and property rows.

Challenges

  1. Add a visibility toggle at the right end of each hierarchy row: ImGui::SameLine(ImGui::GetWindowWidth() - 40) followed by SmallButton(e->visible ? "o" : "-"). Because the node spans the full width, you will need ImGuiTreeNodeFlags_AllowOverlap on it so the button can still be clicked.
  2. Add "Delete all hidden" to the empty-space context menu. Do it with deferred deletion and make sure it works when several hidden entities are next to each other.
  3. Make Ctrl+click on a row log "Ctrl+clicked X" instead of selecting (read ImGui::GetIO().KeyCtrl). This is where multi-select would start.
