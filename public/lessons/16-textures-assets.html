How a texture reaches ImGui

Dear ImGui never loads, owns or even understands textures. To ImGui, a texture is an opaque number, ImTextureID, that it stores in a draw command and passes back to the renderer backend. The OpenGL2 backend treats that number as a GLuint and calls glBindTexture with it. So drawing your own textures is just a cast:

GLuint tex;                                   // created the OGL.c way
glGenTextures(1, &tex);
glBindTexture(GL_TEXTURE_2D, tex);
glTexImage2D(GL_TEXTURE_2D, 0, GL_RGBA, w, h, 0, GL_RGBA, GL_UNSIGNED_BYTE, pixels);

ImTextureID id = (ImTextureID)(intptr_t)tex;  // GLuint -> ImTextureID (a 64-bit integer here)
ImGui::Image(id, ImVec2(128, 128));

The engine wraps this for you. gTextures[i] holds the name, size and glId, and Engine_TexID(i) returns the ready-cast ID (or 0 for an invalid index).

Same texture, two users

The GLuint that textures the crate in the 3D view is the same object ImGui draws in the asset browser. There is no copy. If you change the texture (for example with glTexSubImage2D), both views update.

Image and its UV rectangle

void Image      (ImTextureID tex, const ImVec2& size, const ImVec2& uv0 = ImVec2(0,0), const ImVec2& uv1 = ImVec2(1,1));
void ImageWithBg(ImTextureID tex, const ImVec2& size, const ImVec2& uv0, const ImVec2& uv1,
                 const ImVec4& bg_col = ImVec4(0,0,0,0), const ImVec4& tint_col = ImVec4(1,1,1,1));

uv0 is the texture coordinate at the image's top-left corner and uv1 at its bottom-right. Changing them gives you most "image viewer" features for free:

Effectuv0uv1Why it works
Normal(0,0)(1,1)
Tile 4x(0,0)(4,4)engine textures use GL_REPEAT
Flip vertically(0,1)(1,0)swap the V coordinates
Zoom into a corner(0,0)(0.25,0.25)sub-rectangle = 4x magnified
One cell of a 4x4 atlas(c/4, r/4)((c+1)/4, (r+1)/4)sprite sheets, icon atlases
Render-to-texture images are upside down

OpenGL's texture origin is bottom-left, but ImGui draws top-down. Images you upload from memory look right because row 0 lands at the top. When you show an FBO colour attachment (a "Game View", see lesson 19), pass uv0 = (0,1), uv1 = (1,0) to flip it.

Tint multiplies every texel, so use (1,1,1,0.4) for a faded "disabled" look and (1,0.5,0.5,1) for a red error tint. Background fills in behind transparent pixels. Both live in ImageWithBg. (Before 1.91.9, Image() itself took a tint, so you will see that in older code.)

The first argument is an ID string because many buttons can show the same texture. Inside a loop, PushID(i) + ImageButton("##thumb", ...) is the usual pattern. The button adds style.FramePadding on each side, coloured with ImGuiCol_Button, so pushing a different button colour is an easy selection highlight.

Building the asset browser

A grid that wraps

ImGui has no "flow layout" widget, but one division gives you the column count:

ImGuiStyle &style = ImGui::GetStyle();
float cellW  = thumb + style.FramePadding.x * 2.0f;
int columns  = (int)((ImGui::GetContentRegionAvail().x + style.ItemSpacing.x) / (cellW + style.ItemSpacing.x));
if (columns < 1) columns = 1;

for (int i = 0; i < gTextureCount; i++)
{
    ImGui::PushID(i);
    ImGui::BeginGroup();                                    // thumbnail + caption act as one item
    if (ImGui::ImageButton("##thumb", Engine_TexID(i), ImVec2(thumb, thumb))) selected = i;
    ImGui::TextUnformatted(gTextures[i].name);
    ImGui::EndGroup();
    ImGui::PopID();
    if ((i % columns) != columns - 1 && i + 1 < gTextureCount) ImGui::SameLine();
}

Resize the window and the grid reflows, because the column count is recomputed every frame. That's immediate mode at work.

Interactions on each thumbnail

  • Click: ImageButton returns true, so select the asset.
  • Double-click: IsItemHovered() && IsMouseDoubleClicked(0) applies it to gSelectedEntity.
  • Hover: BeginItemTooltip() with a big Image inside shows a preview.
  • Drag: source with payload "TEXTURE_INDEX". The drag tooltip shows the image too. Entity rows are targets.

Creating textures at runtime

Engine_CreateTexture(name, w, h, rgba) uploads a tightly packed RGBA8 buffer (4 bytes per pixel, row by row) and returns the new asset index, or -1 when all MAX_TEXTURES slots are used. The generator fills a buffer on the CPU, then uploads it:

static unsigned char px[256 * 256 * 4];                     // static: too big for the stack
for (int y = 0; y < size; y++)
    for (int x = 0; x < size; x++)
    {
        bool a = (((x / cellPx) + (y / cellPx)) & 1) == 0;  // checker test
        unsigned char *p = &px[(y * size + x) * 4];
        p[0] = a ? ra : rb;  p[1] = a ? ga : gb;  p[2] = a ? ba : bb;  p[3] = 255;
    }
int idx = Engine_CreateTexture("MyChecker", size, size, px);

The live preview in the generator window uses no texture at all. It evaluates the same pattern function at 64x64 and draws rectangles with the draw list from lesson 15. Only the "Generate" click touches the GPU.

Loading real image files

For PNG/JPG assets, add the single header stb_image.h: stbi_load(path, &w, &h, &n, 4) gives you exactly the RGBA buffer Engine_CreateTexture wants. Call stbi_image_free afterwards.

Game-engine angle

A real content browser works the same way, at a bigger scale. It scans an assets folder, generates small thumbnail textures (often by rendering each mesh or material into an FBO), caches them on disk and shows them in this exact wrapping grid with drag sources. The payload is usually an asset GUID or path rather than an array index, so it stays valid when assets are added or removed. Keep a "missing texture" placeholder (the magenta checker) for asset IDs that fail to resolve.
